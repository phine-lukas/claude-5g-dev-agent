## 1. Conditional Handover in NTN

### 1.1 Verdict

**Not implemented in OAI — not at the gNB, not at the nrUE, not in any
interface.** There is no partial implementation to extend: CHO is absent end to
end. The Rel-16/17 ASN.1 *types* are present (because OAI compiles RRC 17.3.0,
F1AP 16.21.0 and XnAP 16.2.0 and those grammars contain the CHO IEs), but no C
code ever touches them.

### 1.2 How to verify the absence

The whole gNB/UE source has no reference to conditional reconfiguration:

```bash
grep -rni "conditionalreconfig\|condReconfig\|CondReconfigToAddMod\|condTriggerConfig\|condEventD1\|condEventT1" --include="*.c" --include="*.h" openair2/ openair3/ executables/ | grep -v "MESSAGES/ASN.1"
```

That returns nothing except one unrelated XnAP cause enum
(`openair2/COMMON/xnap_messages_types.h:152`,
`XNAP_CAUSE_RADIO_NETWORK_LAYER_CHO_CPC_RESOURCES_TOBECHANGED`) and the string
"Concho Cellular Telephone Co." in the LTE PLMN table.

Meanwhile the types *do* exist in the grammar OAI compiles:

```bash
grep -n "ConditionalReconfiguration-r16\|CondReconfigToAddMod-r16\|condEventD1-r17\|condEventT1-r17\|choConfig-r17" openair2/RRC/NR/MESSAGES/ASN.1/nr-rrc-17.3.0.asn1
```

### 1.3 What OAI does have for mobility, and what it decides on

| Capability | State | Evidence |
|---|---|---|
| F1 (intra-CU, inter-DU) handover | implemented | `openair2/RRC/NR/rrc_gNB_mobility.c:341` `nr_rrc_trigger_f1_ho()`; `doc/handover-tutorial.md` |
| N2 (inter-gNB, via AMF) handover | implemented | `rrc_gNB_mobility.c:617` `nr_rrc_trigger_n2_ho()`; `doc/FEATURE_SET.md:224` |
| Xn handover | **not implemented** | `doc/FEATURE_SET.md` XnAP section lists only Xn Setup, RAN Paging, Retrieve UE Context. `openair2/XNAP/lib/xnap_gNB_mobility_management.c` can encode/decode HANDOVER REQUEST but nothing in `openair2/RRC/` calls it (`grep -rn "xnap" openair2/RRC/NR/*.c` → empty) |
| Conditional handover (any flavour) | **not implemented** | §1.2 |
| DAPS | not implemented (and 3GPP forbids it for NTN anyway, TS 38.300 V18.11.0 clause 16.14.3.2.1) | — |
| RACH-less handover | not implemented | no `rach-Less` in the RRC 17.3.0 grammar OAI uses; it is a later addition |

The handover decision itself is **RSRP/A3 only**:
`openair2/RRC/NR/rrc_gNB.c:1800-1886` — on a MeasurementReport the CU compares
`neighbourCellRSRP - servingCellRSRP` against `a3_offset*0.5 + hysteresis` and
calls `nr_rrc_trigger_n2_ho()` (no F1 connection to the target) or
`nr_rrc_trigger_f1_ho()` (target DU known). There is no timer, no UE/satellite
geometry, no elevation angle, no TA-based trigger.

Manual triggers exist for testing: `nr_HO_F1_trigger_telnet()`
(`rrc_gNB_mobility.c:392`), `nr_HO_N2_trigger_telnet()` (`:663`), and the
FlexRIC xApp path (`openair2/E2AP/RAN_FUNCTION/O-RAN/ran_func_rc.c:1355,1368`).

OAI's own documentation says the same thing and explicitly leaves NTN triggers
to the user: `doc/handover-tutorial.md`, section "Handovers triggers and NTN"
→ "It is possible to modify the source code to trigger a time-based handover",
and suggests a shell `while true; … sleep 15` loop around the telnet trigger as
the stand-in.

### 1.4 What 3GPP requires for CHO in NTN

- **TS 38.300 V18.11.0 clause 16.14.3.2.2** (`specs/38.300/18.11.0/clauses/16.14.md:121-141`):
  on top of ordinary CHO, NTN adds three trigger conditions —
  measurement event **A4**, a **time-based** condition, and a **location-based**
  condition. Time/location conditions may be configured independently of RRM
  measurements. When a time-based condition is used, the source gNB "should
  consider the time indicated to the UE to decide when to start the **early data
  forwarding**", and "Time-based CHO can be performed via RACH-less".
- **TS 38.331 V17.3.0 clause 6.3.2, `CondTriggerConfig-r16`**: the NTN trigger
  conditions are `condEventD1-r17` (two reference locations + two distance
  thresholds + `hysteresisLocation`) and `condEventT1-r17` (`t1-Threshold`,
  `duration`), plus `condEventA4-r17`. Configuration is carried in
  `ConditionalReconfiguration-r16` / `CondReconfigToAddMod-r16`
  (`condRRCReconfig` = a complete nested `RRCReconfiguration` per candidate).
- **Location-based CHO needs data OAI's SIB19 never carries**: `condEventD1`
  references `ReferenceLocation-r17`, and idle/inactive location-based
  measurement initiation uses `referenceLocation` and `distanceThresh` from
  SIB19 (TS 38.331 V17.3.0 clause 6.3.1, SIB19 field descriptions). See §2.3 —
  OAI fills **only** `ntn-Config` into SIB19.
- **Interfaces:**
  - **Intra-gNB / inter-DU CHO:** F1AP *Conditional Inter-DU Mobility
    Information*, *CHO Trigger* (`CHO-initiation`/`CHO-replace`/`CHO-cancel`),
    *Candidate Cells To Be Cancelled List*, and the **Access Success**
    procedure by which the DU tells the CU which candidate the UE actually
    entered (TS 38.473 V18.11.0 clauses 8.3, 9.2.2; the IEs are already in the
    Rel-16 grammar OAI compiles).
  - **Inter-gNB CHO:** **Xn only.** TS 38.423 V18.9.0 has *Conditional Handover
    Information Request/Ack*, *CHO Trigger*, *Estimated Arrival Probability*,
    CONDITIONAL HANDOVER CANCEL and EARLY STATUS TRANSFER.
  - **NGAP has no conditional handover at all.** `grep -rno "Conditional [A-Za-z]*" specs/38.413/18.11.0/clauses/*.md`
    yields one single hit, unrelated to CHO. What NGAP *does* have for the NTN
    case is **Uplink/Downlink RAN Early Status Transfer** (TS 38.413 V18.11.0
    clauses 8.4.9/8.4.10, 9.3.1.190), explicitly "during NG-based handover with
    **time-based trigger condition**", i.e. NG supports *early data forwarding*
    for a time-triggered handover but **not** multi-candidate conditional
    preparation.

### 1.5 Consequence / what an implementation would have to cover

Ordered by dependency, smallest first:

1. **gNB RRC (CU): build `ConditionalReconfiguration`.** Generate one
   `condRRCReconfig` per candidate (each a full `RRCReconfiguration` with
   `reconfigurationWithSync` obtained from the candidate DU), assign
   `condReconfigId`, and attach `condExecutionCond` → `MeasId`s pointing at
   `CondTriggerConfig` entries in `measConfig`. Today the report configurations
   are built in `openair2/RRC/NR/rrc_gNB.c` (`prepare_periodic_event_report()`
   at 744, `prepare_a2_event_report()` at 773, `prepare_a3_event_report()` at
   803) and use `EventTriggerConfig` only — `CondTriggerConfig` appears nowhere.
2. **nrUE RRC: TS 38.331 clause 5.3.5.13** — store candidate configurations,
   evaluate conditions, execute on trigger, and the associated
   `selectedCondRRCReconfig` reporting. Completely absent today.
3. **F1AP: candidate resource reservation** — UE CONTEXT SETUP/MODIFICATION
   with *Conditional Inter-/Intra-DU Mobility Information*, plus the **Access
   Success** procedure and candidate cancellation. None of the F1AP lib
   (`openair2/F1AP/lib/f1ap_ue_context.c`) handles these IEs today.
4. **Trigger sources for D1/T1** — the CU needs UE location (it has none) and
   satellite ephemeris (today only the DU has it, see §2). This is the
   architectural coupling point between questions 1 and 2.
5. **Xn handover first, if inter-gNB CHO is the goal** — there is no Xn HO at
   all, so inter-gNB CHO is a two-step project. Intra-CU/inter-DU CHO is far
   cheaper because the F1 HO machinery and the F1AP IEs already exist.

## 2. SIB19 and the CU/DU split

### 2.1 Where SIB19 is created and encoded *today* in OAI — in the DU, end to end

| Step | Where | Line |
|---|---|---|
| NTN parameters parsed from the conf file into `ServingCellConfigCommon.ext2.ntn_Config_r17` | `openair2/GNB_APP/RRC_nr_paramsvalues.h` | 103-112 (names), 177-186 (bindings) |
| The DU's SIB list (`du_sibs = [19]`) is read | `openair2/GNB_APP/gnb_config.c` | `fill_du_sibs()` at 1232, called at 2043 |
| `SIB19-r17` structure built from the SCC | `openair2/LAYER2/NR_MAC_gNB/nr_radio_config.c` | `get_SIB19_NR()` at 3125 |
| SIB19 put into the Rel-17 `SystemInformation` message and **UPER-encoded** | `openair2/LAYER2/NR_MAC_gNB/config.c` | `nr_mac_configure_other_sib()` at 1073, SIB19 case at 1147-1155, `encode_sysinfo_ie()` into `cc->other_sib_bcch_pdu[1]` at 1167 |
| SIB1 `si-SchedulingInfo` gets the Rel-17 `schedulingInfoList2_r17` entry for SIB19 | `openair2/LAYER2/NR_MAC_gNB/nr_radio_config.c` | `update_SIB1_NR_SI()` at 2668, Rel-17 branch at 2697-2712 |
| SIB19 broadcast scheduling in the SI window | `openair2/LAYER2/NR_MAC_gNB/gNB_scheduler_bch.c` | `find_sib19_sched_info()` at 512, `schedule_nr_other_sib()` at 664; called from `gNB_scheduler.c:193` |
| The **same** `ntn-Config` is put into `reconfigurationWithSync.spCellConfigCommon` for dedicated signalling (handover) | `openair2/LAYER2/NR_MAC_gNB/nr_radio_config.c` | `get_reconfiguration_with_sync()` at 4310, NTN/epochTime block at 4320-4333 |

`nr_mac_configure_other_sib()` is driven from the **F1 Setup Response**
(`openair2/LAYER2/NR_MAC_gNB/mac_rrc_dl_handler.c:173`) — the DU waits for the
CU's SIBs, then encodes CU-SIBs *and* its own DU-SIBs into two SI messages.

Note a config coupling you will hit immediately:
`update_SIB1_NR_SI()` has `AssertFatal(reg_sib, "At least 1 SIB from SchedulingInfo (SIB2 to SIB14 included) needs to be present")`
(`nr_radio_config.c:2714`). That is why every NTN config file pairs
`cu_sibs = [2]` with `du_sibs = [19]`:

```bash
grep -rn "du_sibs\|cu_sibs" --include="*.conf" .
```

### 2.2 Where the *update* interface is today

```bash
grep -rn "GNB_SAT_POSITION_UPDATE\|gnb_sat_position_update_t\|nr_update_sib19" --include="*.c" --include="*.h" .
```

Two entry points, both landing in the **DU's MAC**:

1. **Function call** — `bool nr_update_sib19(const gnb_sat_position_update_t *)`,
   declared in `openair2/LAYER2/NR_MAC_gNB/mac_config.h:27`, implemented at
   `openair2/LAYER2/NR_MAC_gNB/config.c:1246`. It takes `{sfn, subframe, delay,
   drift, accel, position{X,Y,Z}, velocity{X,Y,Z}}` in *SIB19 units* (ta-Common
   granularity 4.072 ns, position step 1.3 m, velocity step 0.06 m/s), writes
   them straight into the cell's `ntn_Config_r17`, and re-encodes **only** the
   SIB19 SI message (`nr_update_sib19_cell()` at `config.c:1174`, re-encode at
   `config.c:1241`). SIB1 is *not* re-encoded and no SI change notification is
   sent — which is correct, see §2.4.
   The **only** caller today is the RFsimulator channel model:
   `radio/rfsimulator/apply_channelmod.c:137-153`, once per 10 subframes, with
   a comment that in a real system this would come "via an external interface
   (e.g. O-RAN E2 interface) to the MAC layer (in the O-DU)".
2. **ITTI message** — `GNB_SAT_POSITION_UPDATE`
   (`openair2/COMMON/mac_messages_def.h:46`), handled in
   `openair2/GNB_APP/gnb_app.c:203-205`. **Nothing in the tree ever sends this
   message** — it is a prepared hook for an external ephemeris source, currently
   dead code. That is the natural place to wire an O1/E2/custom feed into.

### 2.3 What SIB19 actually contains in OAI (a gap list)

`get_SIB19_NR()` (`nr_radio_config.c:3125-3132`) copies `ntn_Config_r17` and
**nothing else**. So OAI's SIB19 never contains:

- `ntn-NeighCellConfigList-r17` (neighbour satellites' ephemeris) — needed for
  NTN neighbour measurements (TS 38.300 V18.11.0 clause 16.14.3.3);
- `referenceLocation-r17` and `distanceThresh-r17` — needed for location-based
  cell reselection/measurement initiation and conceptually paired with
  `condEventD1` (§1.4);
- `t-Service-r17` — when a quasi-Earth-fixed cell stops serving the area; the
  obvious input for a *time-based* handover trigger.

And inside `ntn-Config`, only these are configurable
(`RRC_nr_paramsvalues.h:103-112`): `ntn-UlSyncValidityDuration-r17`,
`cellSpecificKoffset_r17`, `positionX/Y/Z-r17`, `velocityVX/VY/VZ-r17`,
`ta-Common-r17`, `ta-CommonDrift-r17`. No `kmac`, no
`ntn-PolarizationDL/UL`, no orbital-parameter form of the ephemeris
(`nr_update_sib19_cell()` at `config.c:1214-1218` actively frees any
`orbital_r17` and forces `positionVelocity_r17`).

### 2.4 What the standard says about where SIB19 belongs

This is unusually explicit, and it says **gNB-DU**.

**TS 38.470 V18.5.0 clause 5.2.2 (System Information management function):**

> The gNB-DU is responsible for the encoding of the NR-MIB message. In case
> broadcast of SIB1 and other SIBs is needed, the gNB-DU is responsible for the
> encoding of the SIB1 message, SIB10, SIB12, SIB13, SIB14, SIB15, SIB17,
> SIB17bis, SIB18, SIB20, SIB22, SIB23 and SIB24, and the gNB-CU is responsible
> for the encoding of other SIBs. […]
>
> **NOTE: The SIB19 is generated by the gNB-DU.**

```bash
python3 scripts/spec_lookup.py clause 38.470 5.2.2
```

That NOTE was added specifically for NTN — change history, TS 38.470 V18.5.0
clause 8: `2022-06 | RP-96 | RP-221127 | 0093 | 2 | F | Correction to 38.470 for capturing SIB19 | 17.1.0`:

```bash
grep -n "SIB19" specs/38.470/18.5.0/clauses/8.md
```

**TS 38.473 (F1AP) carries no NTN information whatsoever — in any release.**
This is worth checking yourself because it is the decisive point:

```bash
grep -rioc "NTN\|ephemeris\|satellite\|SIB19" specs/38.473/18.11.0/clauses/*.md | grep -v ":0"
```

→ no hits in V18.11.0 (2026-09). For comparison, "Multicast" has 890 hits and
"IAB" 892 in the same conversion, so this is not a conversion artefact.

Concretely, the two F1 containers both exclude SIB19:

- ***gNB-DU System Information*** (TS 38.473 V18.11.0 clause 9.3.1.18, ASN.1
  `GNB-DU-System-Information`): MIB + SIB1 + extension IEs for SIB10, 12, 13,
  14, 15, 17, 17bis, 20, 22, 23, 24. **SIB19 is not in the list**, so the DU
  does not even report SIB19 content to the CU.
- ***gNB-CU System Information*** (clause 9.3.1.42, `SibtypetobeupdatedListItem`
  with `sIBtype INTEGER (2..32,…)`, `sIBmessage`, `valueTag`): syntactically
  `19` would fit the integer range, but the semantics column says
  > "Values for SIBs generated by the gNB-DU as defined clause 5.2.2 in TS
  > 38.470 [2] … are not applicable in this version of the specifications."

So a CU putting SIB19 into the *SIB type to Be Updated List* is non-conformant.

**The same split holds for dedicated signalling.** `ntn-Config-r17` appears in
exactly three places in TS 38.331 V17.3.0: inside `SIB19-r17`, inside
`NTN-NeighCellConfig-r17` (itself inside SIB19), and in
`ServingCellConfigCommon` (`nr-rrc-17.3.0.asn1:3188, 3203, 10322`).
`ServingCellConfigCommon` reaches the UE inside `CellGroupConfig`, which the
**DU** produces and the CU forwards *without decoding* (TS 38.473 requirement;
OAI implements it that way — `openair2/RRC/NR/rrc_gNB.c:1371-1376` "CU must not
decode/re-encode CellGroupConfig"). Hence the NTN assistance data is DU-owned on
both the broadcast and the dedicated path.

**Why the standard put it there.** TS 38.331 V17.3.0 clause 6.3.2, NTN-Config
field descriptions: `ephemerisInfo`, `epochTime`, `ta-Common`,
`ta-CommonDrift`, `ta-CommonDriftVariant` and `ntn-UlSyncValidityDuration` are
each marked

> "This field is excluded when determining changes in system information, i.e.
> changes to … should neither result in system information change notifications
> nor in a modification of valueTag in SIB1."

reinforced by clause 5.2.2.2.2: the modification-period rule applies to updated
SI messages "other than … and **some NTN-specific information as specified in
the field descriptions**".

That is the whole argument in one sentence: **SIB19 is designed to be rewritten
continuously, in place, with no SI-change signalling and no valueTag bump** —
while the `gNB-CU System Information` mechanism is built *around* valueTags and
a SIB-type list exchanged at F1 Setup / gNB-CU Configuration Update. The two are
architecturally incompatible.

### 2.5 Could the interface be moved to the CU? Three options, assessed

#### Option A — CU encodes SIB19 and ships the octets to the DU over F1

*Mechanism:* reuse `gNB-CU System Information` with `sIBtype = 19`. The ASN.1
permits it (`INTEGER (2..32,…)`).

*Verdict:* **technically possible, explicitly non-conformant, and bad
engineering.**

- Non-conformant per TS 38.473 clause 9.3.1.42 semantics + TS 38.470 clause
  5.2.2 (§2.4). An interoperating third-party DU is allowed to reject it.
- Every ephemeris refresh becomes an F1AP **gNB-CU Configuration Update**
  (a Class-1, acknowledged, SCTP procedure — TS 38.473 clause 8.2.5). With the
  RFsim cadence of one update per 10 subframes that is 100 acknowledged F1AP
  procedures per second per cell. Even at a realistic 1 Hz it is a
  control-plane procedure on the critical path of UL timing accuracy.
- F1 transport delay is now inside the ephemeris validity budget. `epochTime`
  is an SFN/subframe of *the DU's* cell: the CU does not own that clock, so it
  would have to predict the DU's SFN at delivery time. Today the DU writes it
  from its own frame counter (`config.c:1183-1185`, and the explicit comment at
  `nr_radio_config.c:4326-4328` about not having the subframe number).
- In OAI it would also need a bidirectional change: the CU rejects SIB19 in
  `cu_sibs` (`gnb_config.c:2211-2216`, `AssertFatal(… "SIB%d is not a CU SIB"`)
  and the DU would `AssertFatal` on an unknown CU SIB
  (`config.c:1138`, `default: AssertFatal(false, "Invalid or not supported SIB%d")`).

#### Option B — CU distributes *ephemeris data*, DU encodes SIB19 (the "CU as ephemeris broker")

*Mechanism:* the CU receives orbit data once (from the NTN control function /
O1 / a flight-dynamics system) and pushes it to each DU; each DU keeps doing
exactly what it does today — build `NTN-Config`, encode SIB19, pick `epochTime`
from its own SFN, broadcast.

*Verdict:* **conformant, and the right shape — but F1AP cannot carry it.**
There is no F1AP IE for ephemeris in any release (§2.4), so the transport has to
be something else:

- O-RAN **O1** (configuration) or **E2** towards the O-DU — this is literally
  what OAI's own comment proposes
  (`radio/rfsimulator/apply_channelmod.c:150-152`);
- or a proprietary/side-band interface into the already-present, currently
  unused `GNB_SAT_POSITION_UPDATE` ITTI message (§2.2).

The work in OAI is then small and additive: implement a producer for
`GNB_SAT_POSITION_UPDATE`; `nr_update_sib19()` already does the rest and is
already multi-cell aware (`config.c:1262-1270`,
"mac: refactor nr_update_sib19 to iterate all cells", commit `e4c44159`).

#### Option C — keep ephemeris at the DU (status quo)

*Verdict:* conformant, zero work, and fine when each DU is physically tied to
one payload/gateway. It breaks down when **the CU needs the ephemeris too** —
which it does as soon as you want:

- `ntn-NeighCellConfigList` in SIB19 (neighbour-cell ephemeris: the CU owns the
  neighbour relations — see `neighbour_list` in
  `ci-scripts/conf_files/neighbour-config.conf`, parsed at the CU — while each
  DU only knows its own cells);
- CHO with `condEventD1`/`condEventT1` (§1), since the CU builds `measConfig`;
- `dedicatedSystemInformationDelivery`, which per TS 38.331 V17.3.0 clause
  6.2.2 may carry **SIB19** to a UE with no common search space on its active
  BWP — and `DLInformationTransfer` is generated by the **CU**. (Not implemented
  in OAI; if it were, the CU *would* legitimately need to encode a SIB19.)

### 2.6 Recommendation

1. **Do not move SIB19 encoding to the CU** (Option A). It is explicitly
   excluded by TS 38.470 clause 5.2.2 and TS 38.473 clause 9.3.1.42, and it puts
   an acknowledged F1AP procedure inside the UL-timing validity budget.
2. **If a single source of ephemeris is wanted, make the CU (or an external NTN
   control function) the distributor and keep encoding at the DU** (Option B).
   In OAI that means writing a producer for the already-existing
   `GNB_SAT_POSITION_UPDATE` ITTI message and leaving
   `nr_update_sib19()`/`get_SIB19_NR()` untouched.
3. **The one thing that genuinely belongs at the CU** is the *neighbour* part:
   `ntn-NeighCellConfigList`, `referenceLocation`, `distanceThresh`,
   `t-Service`. Those are policy/topology data the CU already holds. Since
   F1AP has no IE for them, the clean OAI-internal route is to extend the
   DU-side SIB19 builder with fields fed from the same per-cell configuration,
   and — if/when they must come from the CU — carry them over the same
   out-of-band channel as the ephemeris, **not** over `gNB-CU System
   Information`. Any 3GPP-conformant cross-vendor solution would require a new
   F1AP IE (a CR to TS 38.473), which does not exist today.

## 3. N2 handover in NTN

### 3.1 Is it time critical in NTN? — Yes, for two NTN-specific reasons

**(a) Feeder-link switchover makes N2 HO a bulk, deadline-driven procedure.**
TS 38.300 V18.11.0 clause 16.14.4 (`specs/38.300/18.11.0/clauses/16.14.md:191-210`):

> A feeder link switch over may result in transferring the established
> connection for the affected UEs between two gNBs. […] The NTN Control
> function […] determines the point in time when the feeder link switch over
> between two gNBs is performed. The transfer of the affected UE(s)' context
> between the two gNBs at feeder link switch over is performed by means of
> either **NG based** or Xn based handover.

For a **hard** feeder-link switchover "a radio link interruption may occur
during the transition". So N2 HO is not an occasional event triggered by one
UE's radio conditions — it is *every connected UE of a cell, at a time fixed by
orbital mechanics*. TR 38.821 V16.2.0 clause 8.3.6 flags exactly this: "Handover
all connected UEs in a short period can cause significant signalling load."

**(b) NTN cell dwell times are short, and cross-border AMF change forces NG HO.**
TR 38.821 V16.2.0 Table 7.3.2.1.4-1: with a LEO satellite ground speed of
7.56 km/s, a UE stays in a 50 km cell for **6.6 s** and in a 1000 km cell for
**132 s**. Separately, TS 38.300 clause 16.14.6 says that when the gNB detects
the UE is in a different country from the serving AMF it "should perform an NG
handover to change to an appropriate AMF" — again N2, not Xn.

### 3.2 Delay budget — what is actually on the critical path

Propagation delay figures, TR 38.821 V16.2.0 clause 4 Table 4.2-2 / clause 7
Table 7.1-1 (`specs/38.821/16.2.0/clauses/4.md:101`, `clauses/7.md:18-19`):

| Scenario | Max round-trip propagation delay gNB↔UE |
|---|---|
| GEO, transparent payload (service + feeder) | **541.46 ms** (min 477.48 ms) |
| GEO, regenerative (service link only) | 270.73 ms |
| LEO 600 km, transparent | **25.77 ms** (min ~8 ms) |
| LEO 1200 km, transparent | 41.77 ms |
| LEO 600 km, regenerative | 12.89 ms |

Crucial distinction for N2: **in a transparent payload the gNB is on the ground,
so N2/N3 are terrestrial and carry no satellite delay** — all of the delay is on
Uu. In a **regenerative** payload (gNB on board) N2 and N3 run over the feeder
link, so the satellite hop is added to *every* AMF round trip, and the N2
preparation phase (Handover Required → Handover Request → Ack → Handover
Command, i.e. at least 2 AMF round trips) inflates accordingly. TR 38.821
clause 8.3.5.2 notes this: in architectures 3/4/5 "NG traffic needs to be
transported over the SRI".

**Interruption time.** TR 38.821 V16.2.0 clause 7.3.2.1.1
(`specs/38.821/16.2.0/clauses/7.md:831-850`) defines DL interruption as
RRCReconfiguration-with-sync sent → RRCReconfigurationComplete received at the
target, and states for GEO:

> "Without considering latencies such as RRC processing delay and UE retuning
> […] the interruption time would be **2 RTT (about 1080 ms) for downlink and
> 1.5 RTT (about 810 ms) for uplink**."

Applying the same 2·RTT / 1.5·RTT relation to the LEO-600 km figure (25.77 ms)
gives roughly **52 ms / 39 ms** — *that arithmetic is mine, not a spec
statement*, but it is the right order of magnitude and it is comparable to a
terrestrial handover. The honest summary: **GEO N2 handover means ~1 s of user-plane
interruption; LEO is in the tens of milliseconds.**

Two more NTN-specific risks from the same clause:

- **Measurement staleness** (clause 7.3.2.1.2): with ≥0.5 s between measurement
  report and HO command, the measurements that justified the handover may no
  longer be valid → early/late handover.
- **Reduced RSRP contrast** (clause 7.3.2.1.3): NTN beams overlap with little
  signal-strength difference, so A3 — which is the *only* trigger OAI implements
  (§1.3) — distinguishes cells poorly and ping-pongs.

### 3.3 Are packets lost? — In OAI today, yes. Definitively.

3GPP's N2 handover avoids loss with two mechanisms (TS 23.502 V18.14.0 clause
4.9.1.3.3, `specs/23.502/18.14.0/clauses/4.9.md:421-470`):

- **RAN status transfer** — PDCP COUNT preservation (steps 2a–2c);
- **data forwarding**, direct or indirect (step 3), so DL packets already at the
  source are delivered via the target instead of being dropped;
- and for the NTN time-based case, **Uplink/Downlink RAN *Early* Status
  Transfer** (TS 38.413 V18.11.0 clauses 8.4.9/8.4.10) enabling *early* data
  forwarding, which TS 38.300 clause 16.14.3.2.2 explicitly ties to time-based
  CHO.

OAI implements the first and **not** the second:

| Mechanism | OAI | Evidence |
|---|---|---|
| UL/DL RAN Status Transfer (PDCP COUNT) | **implemented** | `openair2/RRC/NR/rrc_gNB_NGAP.c:1608` `rrc_gNB_send_NGAP_ul_ran_status_transfer()`; `:2190` `rrc_gNB_process_NGAP_DL_RAN_STATUS_TRANSFER()`; wired at `rrc_gNB_mobility.c:656` |
| *Direct Forwarding Path Availability* in HANDOVER REQUIRED | **never sent** | `openair3/NGAP/ngap_gNB_mobility_management.c:76-79` — the Handover Required Transfer is encoded as an **empty** structure, with the comment: "it contains only Direct Forwarding Path Availability IE, which is optional and **is not sent**" |
| *DL Forwarding UP TNL Information* in HANDOVER REQUEST ACKNOWLEDGE | **never set** | `ho_request_ack_transfer_t` (`openair2/COMMON/ngap_messages_types.h:600-607`) has only *DL NG-U UP TNL Information*; the encoder `ngap_gNB_mobility_management.c:422-453` fills only `dL_NGU_UP_TNLInformation`. (TS 38.413 V18.11.0 clause 9.3.4.11 lists *DL Forwarding UP TNL Information* as the IE that would be needed.) |
| *UL Forwarding UP TNL Information* from HANDOVER COMMAND | **decoded, then discarded** | decoded at `ngap_gNB_mobility_management.c:510-517` into `ho_command_transfer`, but `rrc_gNB_process_HandoverCommand()` (`rrc_gNB_NGAP.c:1665-1688`) uses only `msg->handoverCommand` and ignores `msg->pdu_sessions[]` entirely — no forwarding tunnel is ever created |
| Early (RAN Early) Status Transfer | **not implemented** | no `EARLY_STATUS` anywhere in `openair3/NGAP/` |

There is also an inconsistency worth a bug report: the target sets
`dataForwardingAccepted = data_forwarding_accepted` for **every** QoS flow
(`ngap_gNB_mobility_management.c:441-443`) while never providing a forwarding
endpoint — it tells the core that forwarding is accepted and then makes
forwarding impossible.

**Where the packets actually go missing.** At the source,
`rrc_gNB_trigger_reconfiguration_for_handover()`
(`openair2/RRC/NR/rrc_gNB_mobility.c:220-247`) sends the HO command together
with an F1AP UE Context Modification carrying
`transm_action_ind = TransmActionInd_STOP`, i.e. the source DU stops
transmitting. From that instant until the UPF path switch completes (after
Handover Notify, TS 23.502 clause 4.9.1.3.3 steps 5–12), the UPF keeps sending
DL packets down the **old** N3 tunnel to the source gNB, which drops them.
The window is the full interruption time of §3.2 plus the AMF/SMF/UPF path
switch — i.e. **well over a second for GEO**, with nothing forwarded.

For TCP that is not just "a few packets": ~1 s of blackhole at any realistic
rate is a multi-RTT stall plus congestion-window collapse, on a link whose RTT
is already ~0.5 s.

**Note the contrast with F1 handover:** in an intra-CU F1 handover PDCP lives in
the CU-UP and survives the DU change, so there is no N3 path switch and no
forwarding problem — only the radio gap. If the deployment allows it, F1 HO is
dramatically better behaved in NTN than N2 HO. OAI even preserves the old DU
tunnel for the reestablishment case (`rrc_gNB_mobility.h`,
`nr_ho_source_cu_t.old_du_tunnel_config`; set at `rrc_gNB_mobility.c:180-184`).

### 3.4 Other NTN-relevant details found in the N2/HO path

- **T304 is hard-coded to 2000 ms** —
  `openair2/LAYER2/NR_MAC_gNB/nr_radio_config.c:4314`,
  `reconfigurationWithSync->t304 = NR_ReconfigurationWithSync__t304_ms2000;`.
  That happens to be generous enough for GEO, but it is not configurable, so
  you cannot tighten it for LEO or stretch it to `ms10000`.
- **`rach_ConfigDedicated` is always NULL** (`nr_radio_config.c:4315`) — every
  handover is contention-based RACH at the target, adding at least one more
  Uu round trip (so ~0.5 s extra on GEO) to the interruption. Contention-free
  RACH would be a cheap win here.
- **The target cell's `epochTime` is approximated.** `get_reconfiguration_with_sync()`
  (`nr_radio_config.c:4320-4333`) sets `epochTime.sfn = frame` and
  `subFrameNR = 0` with the comment "here we don't have access to the current
  subFrame number, so we only set the SFN. the error of up to 10 ms should be
  acceptable for this long running timer." TS 38.331 V17.3.0 clause 6.3.2
  requires that, in a handover, this field be based on the **target cell's**
  timing — in OAI it is the target DU's own frame counter, which is right for an
  intra-DU/inter-DU case but is not synchronised across gNBs for N2 HO.
- **No `ntn-Config` is exchanged between gNBs over N2.** The source's
  `HandoverPreparationInformation` (`rrc_gNB_mobility.c:323`) carries UE
  capabilities and the source `measConfig`; the target's `ntn-Config` comes back
  inside the target's own `CellGroupConfig`. That is correct and conformant —
  worth stating because it is the one piece of NTN handling in N2 HO that does
  work.

### 3.5 Summary answer to question 3

- **Time critical: yes**, but for NTN-specific reasons (feeder-link switchover
  deadlines, 6.6–132 s LEO cell dwell, cross-border AMF change), not because the
  N2 signalling itself is slow — on a *transparent* payload N2 is a terrestrial
  interface and adds no satellite delay. On a *regenerative* payload it does.
- **Packets lost: yes, in OAI today**, because no data-forwarding tunnel is ever
  established (direct or indirect), while the source DU is told to stop
  transmitting at HO-command time. PDCP COUNT is preserved (RAN Status Transfer
  works), so the receiver's sequence state is consistent — the packets are
  simply gone.
- **Delay a problem: for GEO, yes** — ≈1080 ms DL / ≈810 ms UL interruption per
  TR 38.821 clause 7.3.2.1.1, plus contention-based RACH at the target, plus the
  UPF path switch. For LEO it is tens of milliseconds and comparable to
  terrestrial, but it happens far more often.
- **Cheapest improvements, in order:** (1) implement data forwarding over N2
  (the IEs exist in the Rel-15 NGAP grammar OAI compiles); (2) use
  contention-free RACH (`rach_ConfigDedicated`) in the handover command;
  (3) make T304 configurable; (4) prefer F1 handover over N2 wherever the
  deployment permits — it has no N3 path switch at all.

## 5. One-line answers

1. **CHO in NTN:** absent from OAI entirely (gNB, UE, F1AP, XnAP). The ASN.1
   types are compiled in; no code uses them. OAI's only handover trigger is
   RSRP/A3, which TR 38.821 clause 7.3.2.1.3 says is the wrong trigger for NTN.
   Inter-gNB CHO additionally requires Xn handover, which OAI also lacks; NGAP
   has no CHO at all.
2. **SIB19 CU/DU:** created and encoded in the **DU** (`get_SIB19_NR()` →
   `nr_mac_configure_other_sib()`), updated through `nr_update_sib19()` with a
   prepared-but-unused `GNB_SAT_POSITION_UPDATE` ITTI hook. 3GPP mandates this —
   TS 38.470 clause 5.2.2 NOTE, and F1AP contains no NTN IE in any release.
   Moving the *encoding* to the CU is non-conformant and puts an acknowledged
   F1AP procedure in the UL-timing budget; distributing *ephemeris* from the CU
   while the DU keeps encoding is fine, but needs a non-F1 channel (O1/E2 or the
   ITTI hook).
3. **N2 HO in NTN:** time-critical because feeder-link switchover moves whole
   cells of UEs on an orbital deadline. In OAI, packets *are* lost: no data
   forwarding is set up in either direction, while the source DU is stopped at
   HO-command time. GEO interruption ≈1 s (TR 38.821 clause 7.3.2.1.1); LEO tens
   of ms but far more frequent.
